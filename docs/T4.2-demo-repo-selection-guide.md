# T4.2: Demo Repository Selection and Fork Guide

**Task Owner:** Dev 4 (Infra / Bob Shell)  
**Time Budget:** 15 minutes  
**Dependencies:** None

## Overview

Select and fork a demo repository that will showcase OnboardOps' capabilities. The repository must have specific characteristics that make the demo dramatic and effective.

## Acceptance Criteria

✅ Fork URL pinned in the team channel  
✅ Selection rationale in `notes/demo-repo-choice.md`

## Selection Rubric

The demo repository MUST meet these criteria:

### (a) Size: 10-30 Source Files
- Not too small (trivial to understand)
- Not too large (overwhelming for a 60-second demo)
- Sweet spot for demonstrating cartography

### (b) Real Test Suite
- Must have actual tests (not just stubs)
- Demonstrates OnboardOps can identify test patterns
- Shows value of understanding test coverage

### (c) Onboarding "Trap"
- **CRITICAL:** Must have at least one non-obvious setup step
- Examples:
  - Hidden environment variable requirement
  - Non-standard port configuration
  - Counterintuitive dependency installation order
  - Database initialization quirk
  - Version-specific requirement not in README

**Why the trap matters:** This is what makes the demo dramatic. OnboardOps should catch and auto-recover from this trap, while a human would struggle.

## Recommended Choice: Option 1 (full-stack-fastapi-template)

### Rationale

1. **Maximum Drama:** Multiple onboarding traps create compelling demo moments
2. **Real-World Relevance:** Full-stack apps are what developers actually onboard to
3. **Auto-Recovery Showcase:** Docker, env vars, and ports provide rich recovery scenarios
4. **Complexity Balance:** Complex enough to be impressive, not so complex it's confusing
5. **Test Coverage:** Comprehensive tests demonstrate OnboardOps' understanding capabilities

### Key Traps to Exploit in Demo

1. **Docker Not Running**
   - Detection: `docker ps` fails
   - Recovery: Start Docker Desktop, wait for ready state

2. **Missing .env File**
   - Detection: Import error or config error
   - Recovery: Copy from .env.example, populate with defaults

3. **Port 8000 Already in Use**
   - Detection: "Address already in use" error
   - Recovery: Kill process on port 8000 or use alternative port

4. **Database Not Initialized**
   - Detection: Connection refused or table not found
   - Recovery: Run migrations, seed data

5. **Node Version Mismatch**
   - Detection: Package.json engines check fails
   - Recovery: Switch to correct Node version via nvm

## Manual Steps Required

### Step 1: Evaluate the Candidates

Visit each repository and assess:
- File count: `find . -name "*.py" -o -name "*.js" -o -name "*.ts" | wc -l`
- Test presence: Look for `tests/` or `test_*.py` files
- README complexity: How many setup steps?
- Hidden traps: What's NOT in the README?

### Step 2: Fork the Selected Repository

```bash
# Using GitHub CLI (recommended)
gh repo fork tiangolo/full-stack-fastapi-template --org YOUR_TEAM_ORG --fork-name onboardops-demo

# Or via GitHub web interface:
# 1. Visit https://github.com/tiangolo/full-stack-fastapi-template
# 2. Click "Fork" button
# 3. Select your team organization
# 4. Name it: onboardops-demo
```

### Step 3: Document Your Choice

Create `notes/demo-repo-choice.md` with:
- Selected repository and fork URL
- Rationale (why this one?)
- Identified traps (at least 3)
- Expected demo flow

### Step 4: Share with Team

```bash
# Pin the fork URL in your team channel
# Example message:
"🎯 Demo repo selected: [fork-url]
Rationale: Full-stack FastAPI template with Docker, env vars, and port traps.
See notes/demo-repo-choice.md for details."
```
